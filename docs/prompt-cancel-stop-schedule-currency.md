## 2. Measured facts about the cancel bug

All of this was read from the current source, and two items were observed
running. Do not re-derive it; do verify it still holds.

### 2.1 An in-flight batch cannot be interrupted — the primary cause

`GopClient.request()` in `lib/gop-client.ts` calls `fetch` with **no timeout and
no `AbortSignal`**:

```ts
const response = await fetch(url, { method, headers, body });
```

`runBatches` in `worker/index.ts` consults the cancel flag **only between
batches**:

```ts
if (await isCancelled(jobId)) { cancelled = true; return; }
const batch = plan.batches[index];
...
const outcome = await plan.run(batch, offset);   // ← can block indefinitely
```

So a site that accepts the connection and never answers — an overloaded shop, a
hung PHP-FPM pool, a firewall that blackholes the response — holds that lane for
ever. The run sits at `running`, `processed` never moves, and Cancel does
nothing at all. **This is the most likely thing the operator is reporting.**

With `threads: 10` and a merely slow site, up to 10 further batches also complete
after Cancel is pressed, because each lane only checks at its own boundary. At
`batchSize: 50` that is up to 500 more products. To the operator that is
indistinguishable from "it ignored me".

### 2.2 A redelivered job re-runs even when the database says cancelled

`runJob` checks only that the run exists:

```ts
const state = await getJobState(jobId);
if (state === null) { ...return; }
```

It never looks at `state.status`. So a job the queue hands over a second time is
executed again from the beginning — `markRunning()` flips the status back to
`running` — even if Postgres already says `cancelled`.

**Observed.** In a throwaway stack I let a run finish, then re-added the same job
id to the queue: `runJob` executed again and rewrote the run's status. Redelivery
is not hypothetical — see §2.4.

### 2.3 The cancel flag is deleted at exactly the wrong moment

`finishJob()` in `lib/jobs.ts` ends with:

```ts
await redis.del(KEY.jobCancel(id));
```

So the moment a cancelled run finishes, the only record that anyone asked it to
stop is gone from Redis. Combine with §2.2: a redelivery after a cancel finds no
flag, and runs the whole payload to completion.

The durable record — `job.status = 'cancelled'` in Postgres — exists and is
correct. Nothing consults it.

### 2.4 Redelivery is a normal production event

The worker is constructed with no lock or stall configuration:

```ts
const worker = new Worker<{ jobId: string }>(QUEUE_NAME, runJob, {
  connection: workerConnection,
  concurrency: CONCURRENCY,
});
```

so BullMQ's defaults apply — `lockDuration` 30s, `stalledInterval` 30s,
`maxStalledCount` 1. A worker restart, a redeploy, or an event loop blocked past
the lock window marks the job stalled and hands it to a worker again.

### 2.5 Cancelling a job that has just become active can 500

`requestCancel()` reads the state and then removes:

```ts
const job = await importQueue.getJob(id);
const state = await job?.getState();
if (job && (state === "waiting" || state === "delayed")) {
  await job.remove();
  await finishJob(id, "cancelled", null);
}
```

If the worker picks the job up between `getState()` and `remove()`, BullMQ throws
(`could not be removed because it is locked`), the exception escapes
`app/api/jobs/[id]/cancel/route.ts`, and the operator gets a 500. The flag was
already set, so the run would still stop — but the screen says the cancel failed.

### 2.6 One click can create several runs; Cancel stops one of them

`POST /api/import` with several `storeIds` creates one job per site sharing a
`groupId`. The per-run Cancel acts on a single id, so the siblings carry on. The
Activity list shows them as separate rows, which is honest, but "I cancelled the
import and it kept importing" is the natural way to describe it.

`cancelMany` already exists and the screen has a bulk cancel; there is no
"cancel this whole group".

### 2.7 A stale flag can cancel a future run spuriously

**Observed.** Cancelling a run that has already finished sets the flag and
nothing clears it, because `finishJob` already ran. `CANCEL_TTL_SECONDS` is
24 hours (`lib/redis.ts`), so the key lingers. If that job id is ever redelivered
inside the day it is cancelled immediately for no reason.

### 2.8 A dropped batch index

In `runBatches`, `const index = cursor++` happens **before** the cancel check, so
the batch at that index is consumed and abandoned rather than left for another
lane. Harmless while cancelling (the run is stopping anyway) but it means
`processed` can be short by up to `lanes` batches for reasons unrelated to the
cancel. Worth a comment or a fix while you are in there.

Write that red test first. Something that accepts a TCP connection, reads the

## 4. What to build

### 4.1 Make cancel stop the run

Three changes, and all three are needed — each one alone leaves a hole:

1. **Give every request a deadline and make it abortable.** Add a timeout to
   `GopClient.request()` (an `AbortSignal`, configurable, with a sane default),
   so no batch can block for ever. Then pass a signal down from the worker so a
   cancel aborts the in-flight request rather than waiting for it to finish.
   Decide and document what an aborted batch records: an aborted batch is not the
   same as a failed one, and marking 50 products `batch_failed` because the
   operator pressed Cancel would be a lie in the results table.

2. **Make `runJob` trust Postgres, not the queue.** Return immediately when
   `state.status` is already `cancelled`, `completed` or `failed`. This is the
   fix for §2.2 and costs one query.

3. **Stop deleting the cancel flag on a cancel.** Keep it for its TTL so a
   redelivery is still stopped, or drop the flag entirely and read
   `job.status` between batches instead. If you choose the database, note the
   comment in `lib/redis.ts` claiming a per-batch database round trip would be
   "pure waste" — with `batchSize: 50` and batches measured in seconds, one
   indexed primary-key lookup per batch is not waste, and it removes a whole
   class of Redis/Postgres disagreement. Whichever you pick, make the reasoning
   explicit.

Also fix §2.5 (do not let `job.remove()` throw out of the route) and §2.7 (do not
leave a flag on an already-finished run). Decide whether Cancel should act on a
whole `groupId` (§2.6); if it should, say so on screen, because "cancel 5 runs"
and "cancel this run" are different promises.

### 4.2 Stop, as distinct from Cancel

Cancel is graceful: the worker stops at a batch boundary so no product is cut off
mid-write. That property is deliberate and documented and must survive.

**Stop** is for the case Cancel cannot serve: a run wedged in a request that will
never return, or one the operator needs to end now. Define it as the harder
action — abort the in-flight request immediately, mark the run `cancelled`, and
release the queue job — and make the interface say plainly how it differs. Two
buttons that look alike and behave differently is worse than one.

Whatever you decide, be explicit about what is *not* guaranteed after a Stop: the
plugin may already have committed the batch it was sent, so the site can hold
products the results table does not list. Say that on screen. The removal screen
already sets the standard for this kind of honesty.

Stop must respect the same rules as Cancel: ownership (`lib/ownership.ts`, 404 for
a member touching another account's run) and the acting-as model.

### 4.3 Delete, and scheduled runs, on Activity

**Delete.** `DELETE /api/jobs/[id]` and `forgetJob()` already exist, and
`forgetJob` deliberately refuses a `running` or `queued` run. The Activity list
has no delete control — add one, single and bulk, matching the existing bulk
cancel. Deleting takes `job_item`, `job_result` and `job_batch` with it by
cascade, which for a large run is the only way to reclaim the space; say how many
rows will go before asking for confirmation.

**Scheduled runs.** BullMQ already supports this: `importQueue.add()` takes a
`delay`. Two things make it less simple than it looks:

- The staged payload is durable — `enqueueJob` writes `job_item` inside the same
  transaction as the run row — so a run scheduled for tomorrow does **not**
  depend on the preview, which expires after an hour (`PREVIEW_TTL_MS` in
  `lib/preview.ts`). Confirm that and lean on it.
- A scheduled run must show as scheduled, not as `queued`. `JobStatus` currently
  has `queued | running | completed | failed | cancelled`. Decide whether to add
  a status or carry a `scheduledFor` timestamp, and remember every screen that
  reads `status` — the status bar, the dashboard, `computeStats`, the Activity
  filters. A new enum member with no migration is a runtime error waiting in
  `toState()`.

Cancelling a scheduled run already works (`requestCancel` removes `delayed`
jobs), so keep that path intact.

Per-account limits apply: a scheduled import is still an import, so
`checkImport()` has to run — decide whether at scheduling time, at execution
time, or both, and say why. An account whose import permission is revoked between
scheduling and firing is the interesting case.

### 4.4 Currency — read this before designing anything

**There is no hard-coded VNĐ in this codebase.** Verified: no currency symbol,
no currency field, no money formatter anywhere in `lib/`, `app/`, `components/`,
and nothing in the plugin either. `grep -rn "VND\|VNĐ\|₫\|currency"` over both
repositories returns nothing relevant.

What actually happens: the plugin writes `_price`, `_regular_price` and
`_sale_price` as raw numbers into `postmeta`, and **WooCommerce renders them
using the site's own `woocommerce_currency` option**. In the WordPress end-to-end
run the same payload displayed as `$199,000.00`, because that test site was set
to USD. The VNĐ the operator sees is their shop's setting.

This matters because **stock WooCommerce has no per-product currency.** One shop
has one currency. So "choose the currency when publishing" can only mean one of
these, and they are very different:

| Option | What it does | Consequence |
|---|---|---|
| **A. Display only** | The app shows prices with a chosen symbol in the preview, review table and results, so the operator can see what they are publishing | Changes nothing on the site. Cheapest, honest, and does not pretend to more than it does |
| **B. Set the site's currency** | A run also writes `woocommerce_currency` for the target site | Repricing an entire existing catalogue as a side effect of one import. Dangerous, and needs a plugin endpoint plus a very loud confirmation |
| **C. Convert on the way in** | The operator gives a source currency and a rate; the app multiplies prices before publishing | Numbers stop matching the source file. Needs the rate recorded on the run for ever, or nobody can explain the prices later |

**Ask the owner which of these they meant before building any of it.** My reading
of "chọn đơn vị tiền tệ hiển thị" is **A** — the word *hiển thị* is "display" —
and A is also the only one with no way to damage a live shop. If A is right, a
sensible shape is: currency as a per-account setting (`settings`, beside the
import defaults) with an optional per-run override, used for formatting only,
with a `formatMoney()` added to `lib/format.ts` beside the existing `en-GB`
pinning and its hydration note.

If B is ever wanted, treat it as its own task with its own confirmation design.
Do not fold it into a display change.

## 6. Traps already hit — do not rediscover these

- **`pg` does not work under Turbopack here.** The driver is postgres.js
  (`drizzle-orm/postgres-js`). Do not switch back.
- **`ioredis`, `bullmq` and `postgres` must never reach a Client Component.**
  Pure helpers a client needs live in `lib/store-links.ts`,
  `lib/plugin-version.ts`, `lib/purge-options.ts`. `Can't resolve 'net'` means a
  client component imported a server module.
- **`import "server-only"` throws outside a React Server Component.** It is in
  `lib/preview.ts`, `lib/ownership.ts`, `lib/view.ts`, `lib/audit.ts`. A plain
  Node script — a test, a repro — cannot import those. Insert rows with drizzle
  directly instead; `tests/isolation.ts` already does this for previews.
- **Deleting `.next` breaks typecheck** until `next typegen` runs again.
- **`react-hooks/set-state-in-effect` is an error, not a warning.**
- **Anything derived from "now" must not be rendered during SSR** — React
  hydration error #418. Use `DateTime`, `RelativeTime`, `ElapsedTime`,
  `useHydrated` from `components/ui/client-time.tsx`. This bites a "scheduled
  for" countdown directly.
- **A stale `.next` produces a phantom #418.** Rebuilding over an existing
  `.next` in a shared volume gave mismatched chunks and a hydration error that
  looked like an app bug and was not. Build clean before believing one.
- **The plugin caps batches at 50.** `MAX_BATCH_SIZE` and `MAX_DELETE_BATCH` are
  hard limits on one HTTP request, not on what one run covers.
- **drizzle-kit needs a TTY for rename prompts.** A migration that both drops and
  adds a column in one table cannot be generated headlessly — split it into two
  unambiguous migrations. And **check the generated SQL**: it has emitted a
  composite primary key *before* the column it names, and left dropping an old
  key as a commented TODO.
- **zsh does not word-split unquoted variables.** Building a string of
  `docker run` flags and passing it as `$FLAGS` sends one argument. Pass them
  inline or use an array.
- **`wp-cli` runs in its own container** in these harnesses, so `localhost` there
  is not the web server. Call the site from the host over the mapped port, or
  `docker exec` into the web container.
- **`Actions::install()` in the plugin ends in `wp_safe_redirect()` + `exit`**, so
  anything after it in a `wp eval` never runs.
